# CRM автомалярки — перша версія

## Локальний запуск

Потрібен Node.js 24 (або Node.js 22.13+ із підтримкою `node:sqlite`).
Ключі вашого development-застосунку Clerk мають бути в `.env.local`.

```powershell
npm.cmd install
npm.cmd run dev
```

Відкрийте `/dashboard/clients`, увійдіть через Clerk.
SQLite автоматично створить порожню базу `data/crm.sqlite` під час першого звернення до CRM.
Встановлювати окремий сервер бази даних і запускати міграції вручну не потрібно.

## Один адміністратор

Перший авторизований користувач, який відкриє один із розділів CRM, стає її
єдиним адміністратором. Його Clerk user ID зберігається в базі. Інші облікові
записи не можуть читати або змінювати CRM, включно з прямими викликами Server Actions.
Це обмеження стосується CRM; демонстраційні сторінки шаблону мають власні правила доступу.

Щоб заздалегідь обрати адміністратора, до першого відкриття CRM додайте в `.env.local`:

```dotenv
CRM_ADMIN_USER_ID=user_ваш_id_із_Clerk
```

Зміна цієї змінної не передає права від уже записаного адміністратора іншому.
Не видаляйте базу для зміни адміністратора: разом із нею видаляться робочі дані.

## Перший робочий сценарій

### Клієнти та автомобілі

Меню **Клієнти та автомобілі** має окремі підпункти **Клієнти**
(`/dashboard/clients`) та **Автомобілі** (`/dashboard/vehicles`). На сторінці авто
можна створити автомобіль незалежно від клієнта й пізніше натиснути
**Закріпити клієнта**. Для заявки автомобіль уже має належати вибраному клієнту.

У створенні авто обов’язкові лише **марка, модель і рік**. VIN, держномер та
клієнт необов’язкові. Марка, модель і рік вибираються зі списків. Першими в
групі «Останні використані» показуються до п’яти різних значень із останніх
збережених авто; моделі враховуються окремо для вибраної марки. Для перших
записів, коли історії ще немає, відображається звичайний довідник.

Довідник використовує відкритий [NHTSA vPIC API](https://vpic.nhtsa.dot.gov/api/)
і локальний резервний перелік поширених марок та моделей. Відповіді зовнішнього
каталогу кешуються, а при недоступності джерела доступні резервний перелік
і раніше збережені значення.

Кнопка **Заповнити за VIN** надсилає VIN до vPIC і заповнює доступні марку,
модель та модельний рік. VIN не розкриває повну історію авто; модельний рік
може відрізнятися від календарного року виробництва. Покриття vPIC неповне,
особливо для авто поза ринком США: перевірте отримані значення перед збереженням.
Невдале декодування не заважає вибрати значення вручну зі списків.

Підказка про VIN доступна через іконку ⓘ біля поля: наведенням миші або
фокусом із клавіатури. Успішне декодування не показує окремого попередження.

У рядку автомобіля меню **Дії** містить картку та історію, редагування,
закріплення клієнта для вільного авто, копіювання VIN і видалення з підтвердженням.
Авто з будь-якими заявками або замовленнями видаляти не можна. Для такого авто
також захищено наявний VIN і прив’язку клієнта; держномер, марку, модель та рік
можна виправити. Якщо VIN ще порожній, його можна додати.

Міграція v3 зберігає старі авто й усі зв’язки та додає рік і дату створення.
Рік старих автомобілів залишається невідомим, якщо його раніше не зберігали.

1. **Клієнти та авто** (`/dashboard/clients`): створіть клієнта з іменем і телефоном.
2. У його рядку натисніть **Додати авто**. На одного клієнта можна додати кілька авто.
   Марка й модель обов’язкові; держномер і VIN можна додати пізніше.
3. **Заявки** (`/dashboard/requests`): виберіть клієнта та його автомобіль,
   опишіть роботи. Заявка потрапляє в backlog. VIN ще не обов’язковий.
4. Додайте VIN через рядок заявки або розділ клієнтів. VIN нормалізується у верхній
   регістр і має бути унікальним: 17 латинських літер і цифр, без I, O, Q.
5. Натисніть **Взяти в роботу**, додайте позиції: назва, ціла кількість, ціна за
   одиницю у гривнях. Підсумок рахується автоматично. Заявка перетворюється на
   замовлення в одній транзакції; повторна конвертація неможлива.
6. **Замовлення** (`/dashboard/orders`): відкривайте замовлення й редагуйте опис
   та позиції. Можна створювати замовлення без попередньої заявки, але лише для авто з VIN.
7. **Історія** в рядку клієнта показує замовлення окремо для кожного його автомобіля.

Пошук працює за клієнтом, телефоном, автомобілем, VIN і описом робіт.
Для заявок доступне перемикання між backlog і всіма заявками.
Усі суми зберігаються цілим числом копійок. Початкова валюта — гривня.
Поки не реалізовані оплати, фото й окремий календар.

## Kanban, статуси та дати

У розділі **Дошка робіт** (`/dashboard/kanban`) відображаються реальні дані CRM:
**Backlog → Заплановано → У роботі → Готово → Видано**.
Колонки мають однакову обмежену висоту: заголовки залишаються на місці,
картки прокручуються окремо в кожній колонці, а вся дошка — горизонтально.
Над дошкою є кнопки прокручування ліворуч/праворуч. Вони недоступні на відповідному
краю та автоматично оновлюються після зміни ширини вікна або згортання sidebar.
На мобільних екранах підсумкові показники компактні. Довгі назви обрізаються
в картці, описи обмежені трьома рядками; повні дані доступні у формах.
Ручка підтримує мишу й клавіатуру; Escape скасовує перетягування.
Заявка з датою прийому автоматично потрапляє в «Заплановано»; без дати — у backlog.
Після взяття в роботу на дошці лишається одне замовлення, без дубліката заявки.

Перемістіть картку за ручку або натисніть **Статус і дати**. Перехід відкриває
форму підтвердження; до її збереження зміни не записуються. Взяття заявки в роботу
відкриває створення замовлення з перевіркою VIN і позицій робіт. Замовлення
не можна перетягнути назад у заявки. Картки впорядковані за плановою датою;
довільний порядок усередині колонки не зберігається.

- **Запланований прийом / видача** — поточна домовленість із клієнтом.
- **Фактичний прийом / готовність / видача** — реальні події, окремі від плану.
- Запізнення не змінює запланованих дат автоматично. Прострочені прийом і видача
  позначені на картках. Після фактичної видачі прострочення зникає, а в деталях
  залишається позначка, якщо прийом або видача відбулися пізніше плану.
- Для перенесення наявної планової дати, виправлення факту або повернення статусу
  потрібна причина. Попередній план, зміни фактичних дат і причина зберігаються
  в історії. Вона доступна в діалозі статусів, а для замовлення включає історію заявки.
- Фактичні дати не можуть бути в майбутньому; готовність не може передувати прийому,
  а видача — готовності. Перенесення плану не вимагає змінювати фактичні дати.
- Усі поля — календарні дати. «Сьогодні» визначається в часовому поясі Europe/Kyiv.

При першому запуску нової версії SQLite автоматично застосовує міграцію v2.
Наявні клієнти, авто, заявки, замовлення, позиції та адміністратор зберігаються.
Старі замовлення отримують статус «У роботі»; невідомі планові й фактичні дати
залишаються порожніми. Перед наступною зміною статусу старого замовлення потрібно
вказати реальну дату прийому.

## Зберігання і резервні копії

База розташована на сервері, а не в браузері. Очищення кешу браузера не видаляє дані.
За потреби задайте `CRM_DATABASE_PATH` — абсолютний шлях до SQLite-файлу.
Каталог `data/` виключений із Git.

Для локальної резервної копії зупиніть сервер і скопіюйте весь каталог `data/`.
Під час роботи SQLite може створювати поряд файли `-wal` і `-shm`.
Дані не призначені для ефемерної файлової системи Vercel. Для майбутнього
розгортання потрібен сервер із постійним диском або перенесення шару збереження
на серверну базу. При Docker-розгортанні каталог бази має бути змонтований як volume.

## Огляд автомалярки

Сторінка `/dashboard/overview` показує дані тієї самої CRM-бази, що й інші розділи.
Доступ має лише адміністратор CRM. У меню **Автомалярка → Огляд** доступні:

- активні заявки (backlog і заплановані), замовлення в роботі та готові до видачі;
- кількість і вартість замовлень, фактично виданих у поточному місяці;
- прострочені прийоми/видачі й автомобілі, що очікують видачі;
- планові прийоми заявок і видачі замовлень на 7 днів, включно із сьогодні;
- історія створених заявок та замовлень за 6 місяців, поточне завантаження за статусами;
- останні замовлення, швидке створення клієнта/авто/заявки/замовлення й редагування статусів.

Після конвертації заявка не дублює замовлення в поточному завантаженні. У графіку
створення вона залишається окремою історичною подією. Суми — вартість робіт у гривнях,
облік оплат ще не ведеться. Місячний підсумок використовує фактичну дату видачі;
старі видані замовлення без неї не включаються, їх кількість показується окремо.
Дати та місячні межі визначаються за Europe/Kyiv. Плани не змінюються автоматично.

Спільний кеш CRM оновлюється після збереження будь-якої форми. Поки огляд відкритий,
дані додатково оновлюються щохвилини. Порожня база показує нульові значення й підказки
для початку роботи. Браузерні тести огляду використовують ізольовані тестові дані.

## Перевірки

```powershell
npm.cmd run test:crm
npm.cmd run test:crm:ui
npx.cmd playwright install chromium
npm.cmd run test:crm:browser
npm.cmd run typecheck
npm.cmd run lint
npm.cmd run build
```

Інтеграційні тести використовують окремі тимчасові SQLite-бази і не змінюють
робочу базу. Вони перевіряють VIN, прив’язку авто, суми, конвертацію, відкат
транзакцій, одного адміністратора та збереження після повторного відкриття бази.

Компонентні тести перевіряють реальні форми й Base UI-компоненти: відображення
назв замість ID, залежні списки клієнтів/авто, повідомлення про відсутні опції,
обмеження VIN, помилки збереження і захист незбережених змін у діалогах.

Браузерні перевірки запускають Chromium для desktop (1440×900) і mobile (390×844),
а також перевіряють діалоги за висоти вікна 460 px. Команда спочатку збирає Next.js,
потім запускає ізольований Vite-стенд з реальними CRM-компонентами, CSS та шрифтами
production-збірки. Підмінюється лише сервіс даних і адаптери Next для цього стенду;
Clerk та робоча SQLite-база не використовуються. Це перевірка компонентів у браузері,
а не наскрізний тест авторизації. Тестовий сервер автоматично завершується після тестів.

Стенд використовує реальні `Header`, `SidebarProvider`, `Sidebar` та спільний із застосунком
`DashboardInset`, щоб перевірка враховувала ширину бокового меню. Для дошки окремо
перевіряються розгорнуте/згорнуте меню на 768–1920 px, доступ до «Видано» через кнопки,
повернення до Backlog і зміна розміру до 2560 px. Перевіряються межі самого контейнера,
а не лише `scrollWidth` документа: прихований overflow сторінки не може замаскувати помилку.

Перевіряються таблиці чотирьох розділів, довгі значення, горизонтальне прокручування,
закріплені дії, пошук і пагінація, темна тема, списки вибору та захист змін.
У діалогах прокручується тільки внутрішній контент; заголовок і футер залишаються
на місці. Кнопки футера пов’язані з формою через HTML-атрибут `form`.
Скріншоти та трасування помилок зберігаються в `.artifacts/crm-browser/` (поза Git).
