# CRM автомалярки — перша версія

## Локальний запуск

Потрібен Node.js 24 (або Node.js 22.13+ із підтримкою `node:sqlite`).
Ключі вашого development-застосунку Clerk мають бути в `.env.local`.

```powershell
npm.cmd install
npm.cmd run dev
```

Відкрийте `/dashboard/workspaces`, увійдіть через Clerk і виберіть або створіть
автомалярку. У Clerk мають бути ввімкнені Organizations. SQLite автоматично
створює базу для автомалярки; окремий сервер бази та ручний запуск міграцій
не потрібні.

## Доступ команди

Одна автомалярка відповідає одній Clerk Organization. Ролі Admin і Member
відображаються як адміністратор та виконавець. Адміністратор керує даними й
командою, виконавець читає замовлення та просуває статуси вперед. Сервер
перевіряє чинне членство й роль на кожну операцію. Персональний обліковий
запис без активної організації не має доступу до CRM.

Для старої інсталяції дані `data/crm.sqlite` зберігаються: прив’язати цю базу
до своєї організації може лише записаний раніше власник-адміністратор.
`CRM_ADMIN_USER_ID`, якщо задано, додатково обмежує цю прив’язку, а не замінює
ролі нових організацій. Не видаляйте стару базу для зміни ролей команди.

## Перший робочий сценарій

### Клієнти та автомобілі

Меню **Клієнти та автомобілі** має окремі підпункти **Клієнти**
(`/dashboard/clients`) та **Автомобілі** (`/dashboard/vehicles`). На сторінці авто
можна створити автомобіль незалежно від клієнта й пізніше натиснути
**Закріпити клієнта**. Для заявки автомобіль уже має належати вибраному клієнту.

У створенні авто обов’язкові лише **марка, модель і рік**. VIN, держномер та
клієнт необов’язкові. Марка, модель і рік вибираються зі списків. Першими в
групі «Останні використані» показуються до п’яти різних значень із останніх
збережених авто; моделі враховуються окремо для вибраної марки. Для перших
записів, коли історії ще немає, відображається звичайний довідник.

Довідник використовує відкритий [NHTSA vPIC API](https://vpic.nhtsa.dot.gov/api/)
і локальний резервний перелік поширених марок та моделей. Відповіді зовнішнього
каталогу кешуються, а при недоступності джерела доступні резервний перелік
і раніше збережені значення.

Кнопка **Заповнити за VIN** надсилає VIN до vPIC і заповнює доступні марку,
модель та модельний рік. VIN не розкриває повну історію авто; модельний рік
може відрізнятися від календарного року виробництва. Покриття vPIC неповне,
особливо для авто поза ринком США: перевірте отримані значення перед збереженням.
Невдале декодування не заважає вибрати значення вручну зі списків.

Підказка про VIN доступна через іконку ⓘ біля поля: наведенням миші або
фокусом із клавіатури. Успішне декодування не показує окремого попередження.

У рядку автомобіля меню **Дії** містить картку та історію, редагування,
закріплення клієнта для вільного авто, копіювання VIN і видалення з підтвердженням.
Авто з будь-якими заявками або замовленнями видаляти не можна. Для такого авто
також захищено наявний VIN і прив’язку клієнта; держномер, марку, модель та рік
можна виправити. Якщо VIN ще порожній, його можна додати.

Міграція v3 зберігає старі авто й усі зв’язки та додає рік і дату створення.
Рік старих автомобілів залишається невідомим, якщо його раніше не зберігали.

1. **Клієнти та авто** (`/dashboard/clients`): створіть клієнта з іменем і телефоном.
2. У його рядку натисніть **Додати авто**. На одного клієнта можна додати кілька авто.
   Марка й модель обов’язкові; держномер і VIN можна додати пізніше.
3. **Заявки** (`/dashboard/requests`): виберіть клієнта та його автомобіль,
   опишіть роботи. Заявка потрапляє в backlog. VIN ще не обов’язковий.
4. Додайте VIN через рядок заявки або розділ клієнтів. VIN нормалізується у верхній
   регістр і має бути унікальним: 17 латинських літер і цифр, без I, O, Q.
5. Натисніть **Взяти в роботу**, додайте позиції: назва, ціла кількість, ціна за
   одиницю у гривнях. Підсумок рахується автоматично. Заявка перетворюється на
   замовлення в одній транзакції; повторна конвертація неможлива.
6. **Замовлення** (`/dashboard/orders`): відкривайте замовлення й редагуйте опис
   та позиції. Можна створювати замовлення без попередньої заявки, але лише для авто з VIN.
7. **Історія** в рядку клієнта показує замовлення окремо для кожного його автомобіля.

Пошук працює за клієнтом, телефоном, автомобілем, VIN і описом робіт.
Для заявок доступне перемикання між backlog і всіма заявками.
Усі суми зберігаються цілим числом копійок. Початкова валюта — гривня.
Поки не реалізовані оплати, фото й окремий календар.

## Kanban, статуси та дати

У розділі **Дошка робіт** (`/dashboard/kanban`) відображаються реальні дані CRM:
**Backlog → Заплановано → Створено → У роботі → Готово → Видано**.
Підсумкові картки над дошкою прибрано. Колонки розтягуються за найдовшим списком без обмеження висоти й внутрішнього вертикального скролу; вертикально прокручується вся сторінка. Горизонтальне прокручування залишається спільним для дошки.
Над дошкою є кнопки прокручування ліворуч/праворуч, закріплені під шапкою сторінки під час вертикального скролу. Вони недоступні на відповідному
краю та автоматично оновлюються після зміни ширини вікна або згортання sidebar.
Довгі назви обрізаються в картці, описи обмежені трьома рядками; повні дані доступні у формах.
Ручка підтримує мишу й клавіатуру; Escape скасовує перетягування.
Заявка з датою прийому автоматично потрапляє в «Заплановано»; без дати — у backlog.
Після взяття в роботу на дошці лишається одне замовлення, без дубліката заявки.

Пошук на дошці застосовується через 250 мс після останнього введення. Поле ізольоване від дерева перетягування, а оновлення результатів виконується як React transition. Індекс контактів, автомобілів і описів та порядок за датами обчислюються один раз при зміні даних. Початково відображається до 25 карток на статус. Одна спільна кнопка «Показати ще» під усією дошкою, після останніх відображених карток, додає до 25 наступних карток у кожній колонці. Поруч показано загальну кількість відображених і знайдених карток; після відкриття всіх результатів кнопка зникає. Лічильники й пошук охоплюють усі записи, включно з ще не показаними. Новий запит скидає розмір порцій; скасовані запити та очищення не можуть повернути застарілі результати. Порційним є відображення карток: повний workspace залишається в кеші React Query, без нового серверного запиту на кожен символ.

Перемістіть картку за ручку або натисніть **Статус і дати**. Перехід відкриває
форму підтвердження; до її збереження зміни не записуються. Взяття заявки в роботу
відкриває створення замовлення з перевіркою VIN і позицій робіт. Замовлення
не можна перетягнути назад у заявки. Картки впорядковані за плановою датою;
довільний порядок усередині колонки не зберігається.

- **Запланований прийом / видача** — поточна домовленість із клієнтом.
- **Фактичний прийом / готовність / видача** — реальні події, окремі від плану.
- Запізнення не змінює запланованих дат автоматично. Прострочені прийом і видача
  позначені на картках. Після фактичної видачі прострочення зникає, а в деталях
  залишається позначка, якщо прийом або видача відбулися пізніше плану.
- Для перенесення наявної планової дати, виправлення факту або повернення статусу
  потрібна причина. Попередній план, зміни фактичних дат і причина зберігаються
  в історії. Вона доступна в діалозі статусів, а для замовлення включає історію заявки.
- Фактичні дати не можуть бути в майбутньому; готовність не може передувати прийому,
  а видача — готовності. Перенесення плану не вимагає змінювати фактичні дати.
- Усі поля — календарні дати. «Сьогодні» визначається в часовому поясі Europe/Kyiv.

При першому запуску нової версії SQLite автоматично застосовує міграцію v2.
Наявні клієнти, авто, заявки, замовлення, позиції та адміністратор зберігаються.
Старі замовлення отримують статус «У роботі»; невідомі планові й фактичні дати
залишаються порожніми. Перед наступною зміною статусу старого замовлення потрібно
вказати реальну дату прийому.

## Зберігання і резервні копії

База розташована на сервері, а не в браузері. Очищення кешу браузера не видаляє дані.
За потреби задайте `CRM_DATABASE_PATH` — абсолютний шлях до SQLite-файлу.
Каталог `data/` виключений із Git.

Для локальної резервної копії зупиніть сервер і скопіюйте весь каталог `data/`.
Під час роботи SQLite може створювати поряд файли `-wal` і `-shm`.
Дані не призначені для ефемерної файлової системи Vercel. Для майбутнього
розгортання потрібен сервер із постійним диском або перенесення шару збереження
на серверну базу. При Docker-розгортанні каталог бази має бути змонтований як volume.

## Огляд автомалярки

Сторінка `/dashboard/overview` показує дані тієї самої CRM-бази, що й інші розділи.
Доступ має лише адміністратор CRM. У меню **Автомалярка → Огляд** доступні:

- активні заявки (backlog і заплановані), замовлення в роботі та готові до видачі;
- кількість і вартість замовлень, фактично виданих у поточному місяці;
- прострочені прийоми/видачі й автомобілі, що очікують видачі;
- планові прийоми заявок і видачі замовлень на 7 днів, включно із сьогодні;
- історія створених заявок та замовлень за 6 місяців, поточне завантаження за статусами;
- останні замовлення, швидке створення клієнта/авто/заявки/замовлення й редагування статусів.

Після конвертації заявка не дублює замовлення в поточному завантаженні. У графіку
створення вона залишається окремою історичною подією. Суми — вартість робіт у гривнях,
облік оплат ще не ведеться. Місячний підсумок використовує фактичну дату видачі;
старі видані замовлення без неї не включаються, їх кількість показується окремо.
Дати та місячні межі визначаються за Europe/Kyiv. Плани не змінюються автоматично.

Спільний кеш CRM оновлюється після збереження будь-якої форми. Поки огляд відкритий,
дані додатково оновлюються щохвилини. Порожня база показує нульові значення й підказки
для початку роботи. Браузерні тести огляду використовують ізольовані тестові дані.

## Перевірки

```powershell
npm.cmd run test:crm
npm.cmd run test:crm:ui
npx.cmd playwright install chromium
npm.cmd run test:crm:browser
npm.cmd run typecheck
npm.cmd run lint
npm.cmd run build
```

Інтеграційні тести використовують окремі тимчасові SQLite-бази і не змінюють
робочу базу. Вони перевіряють VIN, прив’язку авто, суми, конвертацію, відкат
транзакцій, ізоляції організацій, ролей та збереження після повторного відкриття бази.

Компонентні тести перевіряють реальні форми й Base UI-компоненти: відображення
назв замість ID, залежні списки клієнтів/авто, повідомлення про відсутні опції,
обмеження VIN, помилки збереження і захист незбережених змін у діалогах.

Браузерні перевірки запускають Chromium для desktop (1440×900) і mobile (390×844),
а також перевіряють діалоги за висоти вікна 460 px. Команда спочатку збирає Next.js,
потім запускає ізольований Vite-стенд з реальними CRM-компонентами, CSS та шрифтами
production-збірки. Підмінюється лише сервіс даних і адаптери Next для цього стенду;
Clerk та робоча SQLite-база не використовуються. Це перевірка компонентів у браузері,
а не наскрізний тест авторизації. Тестовий сервер автоматично завершується після тестів.

Стенд використовує реальні `Header`, `SidebarProvider`, `Sidebar` та спільний із застосунком
`DashboardInset`, щоб перевірка враховувала ширину бокового меню. Для дошки окремо
перевіряються розгорнуте/згорнуте меню на 768–1920 px, доступ до «Видано» через кнопки,
повернення до Backlog і зміна розміру до 2560 px. Перевіряються межі самого контейнера,
а не лише `scrollWidth` документа: прихований overflow сторінки не може замаскувати помилку.

Перевіряються таблиці чотирьох розділів, довгі значення, горизонтальне прокручування,
закріплені дії, пошук і пагінація, темна тема, списки вибору та захист змін.
У діалогах прокручується тільки внутрішній контент; заголовок і футер залишаються
на місці. Кнопки футера пов’язані з формою через HTML-атрибут `form`.
Скріншоти та трасування помилок зберігаються в `.artifacts/crm-browser/` (поза Git).


## Схема кузова та друк замовлення

У формі замовлення є універсальна схема легкового автомобіля: вигляд зверху,
лівий і правий бік, перед і зад. Спочатку виберіть спосіб фарбування (з двох
сторін, з однієї сторони або частково), потім натисніть деталь. Повторне
натискання з тим самим способом прибирає позначку; з іншим — змінює спосіб.
Дрібні деталі також доступні через «Усі деталі списком». Сторони вказані за
ходом автомобіля. Позначки не створюють робіт і не змінюють ціни.

Позиції робіт, кількість і ціни вводяться окремим списком. Схема зберігається
разом із замовленням. Для старих замовлень схема порожня, їхні роботи та суми
зберігаються після автоматичної міграції SQLite до версії 4.

У відкритому збереженому замовленні натисніть «Друк замовлення». Сторінка
`/print/orders/[id]` захищена авторизацією та членством у поточній автомалярці. Вона
містить клієнта, автомобіль, дати, роботи та підсумок; схема з легендою і
переліком позначених деталей починається з нової сторінки A4. Штриховка
розрізняє способи фарбування також у чорно-білому друці. Перед друком потрібно
зберегти зміни; можна скористатися друком браузера або збереженням у PDF.


## Історія статусів і перенесень

Історія показує події поточного запису, а в замовленні — також події пов’язаної
заявки. Новіші події розміщуються першими; при однаковому часі зберігається
порядок запису в базі. Час відображається за Києвом із секундами. Спочатку видно
5 подій, кнопка «Показати ще» відкриває наступні 10.

Кожна подія відокремлює джерело (заявка або замовлення), статус, планові й
фактичні зміни дат «Було / Стало» та примітку користувача. Видалення дати
позначається явно. Старі примітки зберігаються без розбору чи вигаданих фактів:
у давніх подіях фактичні дати можуть бути записані лише текстом. Порожня історія
не означає відсутність попередніх дій — старі записи могли не мати журналу.

Під час аудиту виправлено:

- повторне збереження незміненого стану більше не додає подію;
- фактичні дати нових подій зберігаються структуровано, включно з початковим
  прийомом автомобіля, окремо від причини зміни;
- кожна зміна статусу, дат або примітки збільшує ревізію запису; застаріла
  форма відхиляється, навіть якщо статус не змінився;
- перетворення заявки на замовлення не може відновити план, який уже прибрали
  в іншому вікні;
- міграція v5 зберігає наявні події та додає ревізії без створення фіктивної
  історії. Попередні фактичні дати не відновлюються з поточного стану.

Перевірки причин перенесення, виправлення наявних фактичних дат, хронології
та відповідності дат статусу залишаються на сервері. Оновлення запису й
додавання події виконуються в одній транзакції. Журнал також фіксує опис замовлення, склад робіт, кількість, ціни, підсумок та
схему кузова зі значеннями «Було / Стало». Записи додаються атомарно зі зміною
замовлення; повторне збереження без змін не додає подій. Попередні правки,
зроблені до впровадження цього журналу, не відновлюються заднім числом. Для нових подій зберігаються перевірені сервером ідентифікатор та ім’я автора. Старі події залишаються без вигаданого автора.


## Команда та виконавець замовлення

Виберіть або створіть автомалярку в розділі «Автомалярки». Кожна автомалярка —
окрема Clerk Organization. У розділі «Команда» адміністратор керує запрошеннями
та ролями через Clerk. Admin — адміністратор, Member — виконавець. Запрошення,
яке ще не прийняте, не є активним учасником і не доступне для призначення.

При створенні замовлення або взятті заявки в роботу обов’язково виберіть одного
активного учасника своєї автомалярки. Можна призначити адміністратора. Ім’я
показується в замовленні, списку та дошці. У друкованій версії та PDF інформація
про призначеного виконавця не відображається. Адміністратор може змінити
призначення; історія покаже попереднього й нового виконавця та автора зміни.
Старі замовлення залишаються «Не призначено» до ручного вибору. Після видалення
людини з команди старе ім’я зберігається, але нові призначення їй заборонені.

Виконавець бачить усі замовлення своєї автомалярки, включно з чужими
призначеннями. Ціни, роботи, схема та історія доступні лише для читання.
Кнопки «Позначити готовим» і «Позначити виданим» дозволяють лише наступний
послідовний статус. Дата визначається сервером за Києвом. Редагування плану,
наявних фактичних дат, цін, робіт і призначень залишається адміністратору.
Якщо старому замовленню бракує попередніх фактичних дат, їх спочатку уточнює
адміністратор. Жодна дата не вигадується під час міграції.

Членство й роль перевіряються на сервері за поточними даними Clerk. Організація
береться із сесії; значення форми не можуть змінити її. Кеш даних містить
ідентифікатори організації й користувача та очищається при перемиканні.
Нові події історії зберігають автора; старим подіям автори не дописуються.

Для локальної SQLite-інсталяції кожна нова організація отримує окремий файл
поруч із базою, заданою CRM_DATABASE_PATH. Існуюча база може бути прив’язана
лише її попереднім власником-адміністратором до однієї організації, без
перезапису даних нової автомалярки. CRM_ADMIN_USER_ID стосується власника старої
бази; права в нових автомалярках визначаються ролями Clerk. Зберігайте весь
каталог із базами, включно з файлами організацій і журналами SQLite, на
постійному серверному сховищі.


## Історія клієнта

Дія «Автомобілі та історія» відкриває окремий перегляд автомобілів клієнта.
На комп’ютері обирайте авто зі списку ліворуч, на телефоні — у полі
«Автомобіль клієнта». Автомобілі з активними замовленнями показуються першими.
Картка містить рік, держномер, VIN із копіюванням, кількість активних замовлень
і сумарну вартість робіт за цим автомобілем. Нотатки клієнта можна розгорнути.

Замовлення відображаються від нових до старих: статус, опис, вартість,
дата створення та наявні фактичні дати або план видачі. Спочатку показано
п’ять записів; старіші відкриваються кнопкою «Показати ще». Після відкриття
замовлення можна повернутися кнопкою «До автомобілів клієнта», не втрачаючи
вибір авто. Незбережені правки потребують підтвердження перед поверненням;
після збереження замовлення історія також відкривається з тим самим авто.

Інтеграцію Bidfax відкладено; автоматичні зовнішні запити не виконуються.

## Склад і матеріали замовлення

Розділ «Склад» (`/dashboard/inventory`) ізольований за поточною автомаляркою.
Адміністратор створює позиції: назва, режим обліку, теги й необов’язкова примітка.
У режимі **«За кількістю»** одиниця обирається зі списку «шт», «л», «кг», «м»;
перерахунку упаковок немає. Початковий залишок вноситься надходженням.
Доступні надходження, коригування з обов’язковою причиною та архівування.
Виконавець бачить залишки й історію без можливості змін.
Після першої операції назва, одиниця та режим обліку зафіксовані; теги й примітку
можна змінювати. Архів зберігає історію й залишок, нові списання потребують відновлення.

Для фарби та інших матеріалів без кількісного обліку оберіть **«За сумою»**.
Одиниця виміру, надходження, оцінювання й контроль залишку для цієї позиції
не потрібні. У замовленні адміністратор вибирає матеріал і вводить **«Сума витрати,
грн»**, наприклад 3 500,25. Сума має бути додатною, допускається до двох знаків
після коми; вигадана кількість або початковий запас не створюються. У таблиці
складу показано «Без контролю залишку», а вартість залишку та ціна одиниці — «—».
Ці витрати не змінюють вартість складу.

У збереженому замовленні блок «Матеріали і субпідряд» показує витрати та журнал.
Списання дозволене адміністратору у статусах «В роботі» та «Готово» для чинної
моделі зарплат. Для кількісної позиції вводиться кількість до трьох знаків після
коми; списання понад залишок заборонене. Для позиції за сумою вводиться лише
гривнева вартість. В обох режимах призначення — «Фарбування» (початково) або
«Полірування» — визначає, з бази якого працівника відняти матеріальні витрати.

Редагування створює скасування та новий запис атомарно. Скасування кількісного
списання повертає початкову кількість і собівартість, а витрати за сумою — прибирає
витрату без зміни залишків. Автор, дата, примітка та попередні записи лишаються
в історії. Після готовності зміни автоматично перераховують зарплати та прибуток
за чинними правилами; до готовності матеріали враховуються без нарахування зарплат.

Це внутрішній облік кількості та собівартості: він не змінює ціну
замовлення, а матеріали не показуються в клієнтському PDF. У журналі фіксуються
поточні серверні дата й час, перевірений автор, кількість, причина/примітка та
пов’язане замовлення. Дати відображаються за Києвом; заднє число недоступне.

Міграція SQLite v9 додає `stock_items` та `stock_movements` до наявної
бази кожної автомалярки, без зміни старих замовлень. Кількості зберігаються
цілими тисячними частками; перевірка залишку й операція атомарні. Ідентифікатор
операції захищає від повторного списання при повторенні мережевого запиту.

Міграція SQLite v23 додає режим обліку, зберігає ID, порядок і зв’язки попередніх
рухів. Усі наявні позиції залишаються кількісними. Витрати за сумою зберігаються
в тому самому журналі з нульовою зміною кількості й точною гривневою вартістю;
повтор операції не дублює витрати. Звіти й експорт показують суму без умовних одиниць.

### Собівартість матеріалів (етап 2 економіки замовлень)

При надходженні адміністратор вводить **загальну суму за всю кількість**, валюту
UAH або EUR та курс конкретної закупівлі в гривнях за євро (до шести знаків).
Для гривні курс дорівнює 1. Оригінальна сума, валюта, курс і гривнева вартість
зберігаються в журналі. Нова закупівля змінює середню собівартість лише поточного
залишку та не переоцінює попередні списання.

Списання фіксує вартість за рухомою середньозваженою оцінкою та вид робіт:
«Малярні роботи» або «Полірування». Матеріали відносяться до всього авто.
Картка замовлення показує загальну вартість і розподіл за видами робіт.
Скасування списання повертає його початкову кількість і вартість, навіть після
нових закупівель. Повне списання залишку забирає всю його вартість до копійки.

Додатне коригування кількості потребує оцінки доданого матеріалу; від'ємне
оцінюється автоматично за середньою собівартістю. Причина залишається обов'язковою.

Міграція SQLite v13 зберігає старі складські рухи та залишає їхню вартість
невизначеною. Порожній залишок має нульову вартість. Для непорожнього старого
залишку адміністратор використовує «Оцінити залишок», вводить загальну вартість
у гривнях та підставу оцінювання. Це окремий запис історії, який не змінює
кількість і не переоцінює старі списання. Форма перевіряє і кількість, і версію
залишку; після паралельної операції її потрібно відкрити заново.

Надходження матеріалу з відомою ціною до невизначеного залишку не робить його
вартість відомою. Повернення старого невизначеного списання також потребуватиме
оцінювання нового залишку. Невідомі значення відображаються як «Не визначена»,
а не нулі. Оцінювання й усі інші операції дозволені лише адміністратору;
працівники бачать кількість, вартість та історію.

### Деталізований чек та попередня економіка (етап 3)

У збереженому замовленні адміністратор відкриває «Деталізувати чек». Поточні
позиції та ціни зберігаються у формі; для кожної роботи потрібно вручну обрати
вид: фарбування, розбірка-збірка, підбір фарби, пайка або інший субпідряд.
Фарбування вноситься за деталями, розбірка-збірка — однією загальною позицією.
Частина полірування вказується за всю позицію та вже входить у її клієнтську ціну.

«Відповідальний» організовує замовлення. Маляр, полірувальник і розбірник
призначаються окремо з команди. На кожен вид робіт поки призначається одна людина;
та сама людина може мати кілька ролей. Відсутній виконавець позначається явно,
але не заважає зберегти підготовлений чек. Імена зберігаються в історії незалежно
від подальших змін команди. Нове призначення перевіряється на сервері.

Колорист отримує всю ціну своєї позиції. Для пайки та іншого субпідряду є окремі
ціна клієнту й загальна оплата підряднику; початкова оплата дорівнює ціні позиції
та може бути змінена вручну. Підрядник вводиться за назвою й отримує стабільний
ідентифікатор у межах автомалярки. Однакова нормалізована назва використовує
того самого підрядника, а попередні записи зберігають свої дані.

Після збереження блок економіки показує чек, матеріали, попередню винагороду
кожній ролі, субпідряд і залишок автомалярки. Ставка початково 60% та зберігається
в деталізації замовлення. Матеріали беруться зі складських списань; за невідомої
вартості, відсутнього виду робіт або від'ємної бази CRM показує причину, а не
вигадану суму. До готовності це попередній розрахунок; проведення описано нижче.

Міграція SQLite v14 додає `crm_order_economics` і `crm_contractors`, не змінюючи
старих цін і статусів. Деталізація, клієнтські позиції та історія оновлюються
однією транзакцією. Перевірка версії захищає від паралельного редагування;
звичайна форма не дозволяє змінювати позиції вже деталізованого чека.
Звичайне редагування не дозволяє зменшити чек нижче отриманої оплати. Після
проведення зміни чека та матеріалів доступні через фінансове коригування.

Працівники бачать економіку без редагування. Друкований клієнтський документ
містить тільки роботи, кількість і ціни; внутрішня деталізація вилучається також
із даних документа, включно зі ставкою працівників.

### Нарахування, виплати та коригування (етап 4)

Перший перехід деталізованого замовлення у «Готово» атомарно зберігає версію
економіки, ставку, виконавців і нарахування. Адміністративний перехід одразу
у «Видано» також проводить розрахунок. Невідома собівартість, нерозподілені
матеріали, відсутній виконавець або від'ємна база блокують нарахування і зміну
статусу. Повтор переходу чи повернення в роботу не дублює нарахувань і не
скасовує проведених операцій. Блок економіки показує останню проведену версію.

У «Нарахування та виплати» адміністратор записує аванс до готовності авто,
часткову виплату працівнику або підряднику та фактичне повернення від одержувача.
Баланс у межах замовлення показує нараховано, виплачено, до виплати або
аванс/переплату. Перенесення авансів між авто й автоматичного утримання немає.
Помилковий запис виплати виправляється окремим скасуванням із причиною;
фактичне повернення грошей є іншою операцією. Історія зберігає автора, дату,
суму й причину. Повтор запиту з тим самим ідентифікатором не створює другої операції.

«Фінансове коригування» дозволяє змінити роботи, ціни, ставку, виконавців,
внутрішнє полірування та субпідряд, додати матеріали або скасувати списання.
Причина обов'язкова. Попередній перегляд показує чек, собівартість, залишок
автомалярки та різницю нарахування кожному одержувачу. Перегляд не зберігає
змін. Підтвердження атомарно проводить матеріали, клієнтські позиції та лише
різницю нарахувань; фактичні виплати залишаються без змін. Перевіряються версії
замовлення, розрахунку та всього складу. Після сторонньої зміни потрібен новий
перегляд. Скасоване списання повертає його оригінальну вартість.

Зменшення проведеного чека нижче отриманої оплати показує переплату клієнта.
«Записати повернення клієнту» фіксує фактичне часткове або повне повернення
в межах переплати. Початкова оплата зберігається. Скасування помилкового запису
повернення також має окремий запис; воно не означає фактичного руху грошей.
Надходження на огляді враховують фактичні повернення за датою повернення.

«Ставка для нових замовлень» змінює загальне налаштування автомалярки
(початково 60%). Замовлення запам'ятовує ставку при створенні. Зміна налаштування
не перераховує чинні авто чи історичні нарахування. Працівник бачить економіку
авто та власний журнал розрахунків; фінансові зміни доступні адміністратору.

Міграція SQLite v15 додає незмінні версії розрахунків, журнал виплат і таблицю
повернень клієнтам. Історичні дані зберігаються без вигаданих нарахувань.
Недеталізовані замовлення працюють у попередньому режимі без автоматичних
нарахувань. Для готового або виданого авто без проведення доступний явний
«Початковий розрахунок завершеного авто» з переглядом і підтвердженням.
Зведення описано нижче та у [PRD](../plans/workshop-economics.prd.md).

### Зведення за період (етап 5)

У навігації є «Зведення за період» (`/dashboard/reports`). Початкова вибірка —
від першого дня поточного місяця до сьогодні; можна вказати довільні дати.
Обидві межі включені, часовий пояс — Київ. Період, розділ і спосіб відбору
авто зберігаються в URL. CSV містить усі рядки вибраного розділу, включно
з тими, що не вміщуються на одну сторінку таблиці.

- **Проведення.** Початкові розрахунки та різниці коригувань за датою запису:
  чек, матеріали, нарахування власним виконавцям, субпідряд і залишок після
  прямих витрат. Цей залишок не є чистим прибутком після загальних витрат.
  Окремий журнал клієнтських коштів містить оплати, повернення та скасування
  зі знаком за їхньою датою запису. Виплати працівникам не віднімаються
  з економічного залишку повторно після нарахування.
- **Авто.** Відбір за поточною датою готовності, створення або видачі.
  Суми беруться з останньої проведеної версії не пізніше кінця періоду;
  для авто без проведення показано «Не визначено». Поточний статус і
  метадані авто показано окремо. Фільтр авто не обмежує інші розділи.
- **Матеріали.** Матриця «матеріали × авто» містить кількість і собівартість
  списань мінус повернення за датою складського руху, незалежно від дати
  готовності. Повернення в наступному періоді показано з мінусом у цьому
  періоді. Невідома історична вартість не підміняється нулем. Повне
  скасування невідомого списання в межах одного періоду дає нульовий рух.
- **Розрахунки.** Працівники й підрядники: баланс до початку періоду,
  нарахування, коригування, виплати, фактичні повернення, скасування і
  баланс на кінець. «До виплати» й «Аванси» підсумовані по кожному авто
  окремо, без автоматичного заліку між замовленнями. Є деталізація по
  авто та журнал із причиною, автором і датою.

Скасування помилкового запису в наступному місяці не переписує попередній
місяць цього зведення: протилежна сума потрапляє в період скасування.
Це правило відрізняється від картки замовлення, яка показує поточний стан
усіх його розрахунків.

Адміністратор бачить зведення автомалярки. Працівник отримує тільки власні
розрахунки й власний CSV; адміністративні суми та чужі виплати не входять
у серверну відповідь. Ключі кешу включають організацію, користувача й період;
зміна автомалярки прибирає попередні дані. Формування звіту читає узгоджений
знімок SQLite без нових проведень або міграції схеми.

Адміністратор може додати відсутню модель для вибраної марки прямо у формі автомобіля: «Додати модель» → «Додати й вибрати». Модель зберігається в довіднику поточної автомалярки незалежно від збереження автомобіля та доповнює зовнішній і резервний каталоги. Пробіли нормалізуються, повторні назви без урахування регістру не створюють дублікатів. Власний довідник не розшифровує VIN: якщо провайдер не повернув модель, її потрібно вибрати вручну.

Список замовлень використовує компактний заголовок із пошуком і створенням замовлення (створення доступне адміністратору), без summary-карток. Статус і термін розташовані перед роботами. У таблицях зменшено вертикальні відступи; короткі значення залишаються текстом, обрізані отримують доступний із клавіатури та дотиком popover. Повні описи можна виділити й скопіювати. Роботи, автомобілі клієнта та планові/фактичні дати відкривають структуровані popover з обмеженням розміру за viewport і внутрішнім прокручуванням. Із переліку авто доступна повна історія; відсутній VIN можна додати через відповідну дію. Дії складу перенесені в меню «…», щоб не збільшувати висоту рядків на вузьких екранах.
Фільтр статусів замовлень зберігається у параметрі URL `orderStatus`, працює разом із пошуком і скидає пагінацію при зміні. Кольори статусів відповідають історії: у роботі — бурштиновий, готово — зелений, видано — нейтральний.

### Статуси й оплати

Нове замовлення починається зі статусу «Створено» (жовтий), далі «У роботі» (синій), «Готово» (фіолетовий), «Видано» (зелений). Виконавець просуває статус лише на один крок уперед; початок роботи встановлює фактичний прийом, якщо його ще немає. При створенні фактична дата прийому необов’язкова; план не змінюється автоматично.

Оплата є окремою сутністю: адміністратор записує аванси та часткові платежі у блоці «Оплата» замовлення. Платіж містить суму, поточну дату й час, автора та примітку. Історія зберігається в межах автомалярки. Виконавець має лише перегляд. Переплату заборонено; змінити вартість нижче отриманої суми не можна. Повтор операції з тим самим ідентифікатором не створює ще одну оплату.

Помилковий платіж скасовується повністю з обов’язковою причиною; оригінал не видаляється. Це виправлення запису CRM, а не проведення повернення коштів у банку. Скасований платіж виключається з надходжень за його початковий місяць.

Огляд має довільний період і кнопки «Поточний місяць» (від першого числа до сьогодні) та «Минулий місяць» (повний календарний місяць). Дати включні, часовий пояс — Київ; відбір зберігається в URL. Поточні статуси, завантаженість і черги залишаються на сьогодні. Графік та останні замовлення відбираються за датою створення.

«Завершено за період» відбирає поточні готові замовлення за датою готовності (для старих записів — датою видачі, якщо готовність не вказана). «Прибуток фірми» складається з останнього збереженого результату цих замовлень: чек мінус матеріали, субпідряд і нараховані зарплати. Оплата клієнтом і виплати працівникам на прибуток не впливають. Пізніше виправлення вартості або витрат оновлює прибуток періоду готовності. Оренда й інші витрати поза CRM не враховуються; збиток показується від’ємним. Якщо старе готове авто не має фінансового розрахунку, огляд показує попередження й окремий перехід до таких авто; при повній відсутності розрахунків картка показує «—».

«Надходження за період» — дійсні платежі мінус повернення за датами їх отримання/повернення, незалежно від готовності авто. Скасовані операції не враховуються. «Заборгованість за готовими авто» — поточний залишок за авто, готовими у вибраному періоді. «До сплати за відкритими авто» — поточний залишок за незавершеними авто, створеними у періоді. Це поточний борг, а не відновлений борг на останній день періоду. Видалені в кошик замовлення не враховуються.

Картки відкривають відповідний серверний відбір замовлень до пагінації, з видимим описом періоду й кнопкою скидання. Для поточних статусів відкривається відповідний статус без періоду. Фінансові показники порівнюються з відповідними днями попереднього місяця (повний місяць — з повним попереднім); довільний період — з попереднім періодом тієї самої тривалості.

### Редагування клієнтів і контакти

Натискання імені в таблиці «Клієнти» відкриває модалку редагування; та сама дія є в меню «…». Адміністратор змінює ім’я, нотатки, додає та видаляє телефони й email. Потрібен хоча б один контакт будь-якого типу, дозволено до 20 контактів. Клієнта можна створити лише з email. Нормалізовані дублікати всередині однієї картки заборонені, спільний сімейний контакт у різних клієнтів дозволений.

Джерело контактів — таблиця `crm_customer_contacts` з типом, значенням, нормалізованим значенням та порядком відображення. Поле `Customer.phone` залишене як проєкція першого телефону для сумісності; для email-only клієнта воно порожнє, UI використовує email. Старі телефони переносяться в таблицю контактів автоматично. Незмінені контакти зберігають ID. Оновлення клієнта й контактів атомарне; `revision` захищає від перезапису змін іншого вікна. Доступ на запис і відповідність поточної автомалярки перевіряються на сервері.

Пошук клієнтів, заявок, замовлень, дошки та вибір клієнта враховують усі контакти. Таблиця лишається компактною: повний перелік контактів відкривається в popover з посиланнями `tel:` / `mailto:`. В історії та друкованому замовленні відображаються всі контакти.

### Динаміка карток огляду

Вісім карток мають компактні лінійні графіки Recharts і кольоровий показник зміни в нижньому правому кутку блоку показника, без рамки й фону. Графіки не додають висоти карткам. Поточні статуси порівнюються з таким самим днем попереднього місяця, а фінансові картки — з попереднім періодом за описаними вище правилами. Межі порівняння фінансових показників підписані під картками. Враховано високосні роки, перехід року та часовий пояс Києва.

Для поточних статусів стани на кінець дня відновлюються з журналу; за його відсутності використовуються відомі фактичні дати. Якщо достовірно відновити стан неможливо, графік містить пропуск, а відсоток замінюється поясненням. Поточна точка відповідає основному показнику картки. Якщо фінансовий розрахунок відсутній у частини готових авто поточного або попереднього періоду, відсоток зміни прибутку не показується.

Фінансові мініграфіки накопичують поточні суми для замовлень вибраного періоду; борги використовують сьогоднішній залишок. Історія поточних статусів і далі відновлюється за подіями. Графіки довгих періодів мають не більше 61 точки.

Великі значення карток і фактичного приросту скорочуються до `K` / `M` з точністю до одного десяткового знака (наприклад, `11.2K грн`). Відсотки мають не більше одного десяткового знака й крапку як роздільник (`+102.1%`); зайві нулі не показуються. Розрахунки й доступні назви карток зберігають точні суми.

Формула зміни: `(поточне − попереднє) / |попереднє| × 100`. Якщо попереднє значення нульове: для нульового поточного показано `0%`, для додатного — фактичний приріст (наприклад, `+3`), без некоректного відсотка. Зростання надходжень і кількості виданих авто позначається зеленим; зростання боргу — червоним, його зменшення — зеленим. Інші додатні зміни зелені, від’ємні — червоні; нуль і відсутність історії нейтральні. Лінії промальовуються зліва направо за 900 мс; Recharts вимикає анімацію за системного reduced motion. Графіки та зберігають наявні hover/pressed ефекти карток і підтримку reduced motion.
# Тестове наповнення організації

Генератор додає 300 клієнтів, 500 автомобілів, 200 заявок і 1 000 замовлень.
Замовлення мають позиції робіт, плани фарбування, чинних виконавців, історію
переходів і повні, часткові або відсутні оплати. Історія охоплює приблизно
шість місяців; поточні заявки й замовлення включають прострочені та майбутні плани.
Записи позначені `[ТЕСТ]`, номери авто — `ТЕСТ`, email — `example.invalid`.
VIN синтетичні й не призначені для перевірки зовнішнім декодером.

Запускайте через Node.js 22.13+ у каталозі проєкту (скрипт використовує `node:sqlite`).
Змінні середовища завантажуються через `@next/env`, як у застосунку.
Потрібні доступ до Clerk і доступна локальна база організації. Скрипт не змінює
Clerk: тільки читає організації й учасників. Коли назви дублюються, вкажіть ID.

```bash
# Перегляд цільової бази, кількостей і виконавців без запису
npm run crm:demo -- --organization "АВТО ФАРБА"

# Наповнення; перед записом створюється узгоджена SQLite-резервна копія
npm run crm:demo -- --organization "АВТО ФАРБА" --apply

# Перегляд і видалення саме цього тестового набору
npm run crm:demo -- --organization "АВТО ФАРБА" --remove
npm run crm:demo -- --organization "АВТО ФАРБА" --remove --apply
```

Типовий ідентифікатор набору — `avto-farba-demo-v1`; його можна змінити через
`--run-id NAME`. Повторне завантаження того самого набору завершується помилкою
без додавання записів. Генерація відбувається в тимчасовій базі, імпорт — однією
транзакцією. Нумерація наявних замовлень, налаштування та довідники зберігаються.
Скрипт знаходить файл за збереженим ID організації, враховуючи пріоритет старої
бази `CRM_DATABASE_PATH`, і не створює та не переприв’язує бази організацій.

Резервні копії зберігаються в `backups/` поряд із цільовою базою. Очищення видаляє
весь облік, пов’язаний із тестовими замовленнями (включно з пізнішими оплатами й
подіями), та самі згенеровані клієнти, авто, заявки й замовлення. Якщо на них
посилаються ручні замовлення, заявки або складські рухи, операція відкотиться
повністю; спочатку потрібно розібрати ці залежності. Лічильник номерів замовлень
після очищення не повертається назад. Для іншого сервера скрипт потрібно
запустити там, де лежать його SQLite-файли.
