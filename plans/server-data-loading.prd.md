## Problem Statement

CRM завантажує клієнтів, автомобілі, замовлення, роботи, платежі та історію одним пакетом організації. Основні списки відбирають і розбивають записи у браузері. Склад має серверний пошук, проте також завантажує повний каталог та журнал. Звіти читають повний знімок бази перед відбором періоду. Зі збільшенням історії ростуть передача даних, використання пам'яті, час обробки й навантаження на малий AWS сервер.

## Solution

Кожен розділ отримує потрібну сторінку даних. Сервер виконує пошук, фільтрацію, сортування та пагінацію в SQLite; деталі й журнали завантажуються при відкритті. Огляд отримує підсумки, звіти — дані потрібного періоду. Зберігаємо бізнесові правила, вигляд і можливості CRM та чинний деплой одним Next.js процесом із постійною SQLite базою.

## Implementation Decisions

- Погоджені модулі: серверні списки; деталі та історія; склад і журнал; огляд та звіти; кеш і захист організацій.
- Спочатку зафіксовано попередній стан окремим комітом. Рефакторинг виконується послідовними працездатними частинами, починаючи зі складу.
- Читання списків через GET обробники й сервісний шар. Початкове серверне завантаження використовує той самий контракт читання без внутрішнього HTTP запиту.
- Типізований результат списку: записи, загальна кількість, номер сторінки, розмір сторінки. Типовий розмір 25–50, жорстке обмеження 100. Стабільне сортування з унікальним додатковим ключем. Експорт має окремий явно викликаний шлях.
- Параметризовані SQL запити; пошук і теги відбираються до LIMIT/OFFSET. Український регістр і нормалізація мають зберігати чинну семантику пошуку; SQL LIKE не можна покладатися на стандартний ASCII lower для кирилиці.
- Для матеріалів усі слова пошуку мають збігатися; вибрані теги поєднуються через АБО; текст, теги й архів через І. Розрахунок залишків відбувається лише для вибраних позицій.
- Журнал має стабільний порядок, фільтри матеріалу/замовлення та окрему пагінацію. Підсумки замовлення враховують повний його набір операцій незалежно від сторінки журналу.
- Списки повертають проєкції для таблиць; картка повертає один запис із потрібними зв'язками. Форми отримують довідники через окремі запити пошуку, не через повну CRM.
- Для огляду використовуємо SQL агрегації; для звітів завантажуємо записи відповідного періоду та залежності, потрібні чинним правилам коригувань. Грошові значення залишаються цілими копійками.
- Індекси додаються лише для фактичних умов і сортування, зі зворотно сумісною міграцією. Не замінюємо локальну чи production базу, не змінюємо бізнесові журнали.
- Кожен запит перевіряє автентифікацію, активне членство, організацію та дозволи. Ключі кешу включають користувача, організацію й фільтри. Перенесення попереднього результату між організаціями заборонене.
- Debounce стосується запиту, введення має окремий негайний стан. Запити підтримують скасування; зміна фільтрів скидає сторінку. Помилка запиту не дозволяє експортувати застарілий результат.
- Мутації залишають чинні перевірки й транзакції, інвалідують відповідні списки, картку й підсумки.
- За документацією поточний AWS сервер — ARM64 EC2 t4g.small, 2 ГБ RAM, постійний EBS, один контейнер CRM; збірка в GitHub Actions. Це вихідне обмеження, а не результат поточної перевірки AWS. Не додаємо Redis, окремий бекенд, RDS чи додаткові процеси.
- Для приймання вимірюємо час читання, розмір JSON і пам'ять на тимчасовому наборі щонайменше 10 000 замовлень та 100 000 складських операцій. Фіксуємо середовище й результати; достатність 2 ГБ для реального навантаження оцінюємо за вимірами, а не гарантуємо наперед.

## Testing Decisions

- Погоджені модульні, інтеграційні SQLite та перевірки доступу, браузерні сценарії пошуку, пагінації й картки.
- Тестуємо зовнішню поведінку та правильні результати; не копіюємо реалізацію і не прив'язуємо тести до конкретного тексту SQL.
- Орієнтуємося на наявні тести репозиторіїв із тимчасовими SQLite базами, фінансові сценарії, перевірки HTTP авторизації та Playwright стенд CRM.
- Списки: порожні результати, остання й недійсна сторінка, однакові дати, відсутність пропусків/повторів, загальна кількість, обмеження розміру, зміна фільтрів, кирилиця, апостроф, %, _, SKU, кілька тегів, архів.
- Склад: прихід, списання, повернення та переоцінка, невідома собівартість, історія конкретного матеріалу/авто, експорт усіх знайдених рядків.
- Регресії: суми зарплат та звітів, готовність без оплати, автоматичні коригування, субпідряд, від'ємна маржа, межі звітного періоду й часовий пояс.
- Доступ: 401, неправильна організація, відкликане членство, права працівника, перемикання організації під час запиту, пряме відкриття чужого ID.
- Браузер: введення без затримки, реальні мережеві запити після debounce, повільна/невдала відповідь, збереження фокусу, URL навігація, робота модалок і мутацій на desktop та mobile.
- Навантаження: обмежена кількість повернених рядків при зростанні бази, плани запитів і порівняння часу/JSON/пам'яті; навантажувальні записи лише в тимчасовій базі.
- Обов'язкові перевірки TypeScript, lint, профільні тести й production build. Перевірка на справжньому AWS сервері та деплой є окремими діями; результати локального стенду позначаються як локальні.

## Out of Scope

- Зміни формул зарплати, складської собівартості, оплати, статусів і дозволів.
- Редизайн сторінок і вкладок, зміна довідника тегів.
- Перехід на PostgreSQL/RDS, кілька екземплярів CRM, Redis, окремі мікросервіси.
- Купівля ресурсів, зміна AWS плану, push у main, автоматичний запуск production деплою без окремого доручення.
- Масове виправлення чи видалення клієнтських даних.

## Further Notes

Користувач погодив запропонований обсяг і перевірки. Основний критерій інфраструктури — достатність ресурсів на поточному AWS. Спочатку зменшуємо зайві читання й передачу даних; рішення про масштабування приймаємо за фактичним навантаженням. Зберігаємо можливість звичайного оновлення контейнера з поточними постійними даними та резервними копіями.

Результати реалізації та локальних перевірок наведено нижче. Замір production навантаження AWS залишається окремою перевіркою після погодженого розгортання.

### Реалізовано та перевірено 24.11.2026

- Попередні зміни зафіксовано комітом `82d86ab` до початку рефакторингу.
- Клієнти, автомобілі, заявки, замовлення та кошик отримують сторінки результатів із SQL пошуком, сортуванням і загальною кількістю. Дошка завантажує по 25 карток на статус наступними порціями; зміна або очищення пошуку скидає порцію до першої навіть при використанні кешу.
- Списки отримують підсумок оплат і ознаку пов’язаних документів авто без повних журналів. Збережено статуси оплат, обмеження видалення та повні лічильники огляду.
- Картка, історія авто/клієнта/заявки та історія змін замовлення завантажуються окремо. Довідники форм мають серверний autocomplete зі збереженням вибраного значення; форматований телефон, VIN і переставлені слова зберігають поведінку попереднього combobox.
- Склад отримує доступ і сторінку матеріалів; загальний журнал та історія позиції — окремі запити з пагінацією. Вкладка матеріалів авто отримує лише його операції. Експорт явно отримує всі сторінки поточних результатів. Основні компоненти більше не викликають старі запити повного CRM workspace чи повного складу.
- Огляд розраховується на сервері без завантаження складського та фінансового workspace. Суми робіт підсумовує SQL; історичні тренди використовують проєкцію статусів, дат і змін суми. Ця реконструкція трендів ще залежить від обсягу історії на сервері; первинні історичні масиви не передаються браузеру. Форматувальник київських дат повторно використовується між рядками.
- Зарплати читають записи відповідного періоду та потрібні попередні версії. Зведення отримує початкові залишки через SQL агрегацію, події періоду й початкові операції для скасувань. Інтеграційне порівняння зі старим повним розрахунком підтверджує однакові результати для адміністратора й працівника, переходів між місяцями, пізніших коригувань і скасування виплати.
- Перевірки організації та ролі виконуються на сервері. Ключі кешу та перенесення попереднього результату обмежені користувачем і організацією; зміна фільтра скасовує застарілі запити. Мутації оновлюють відповідні списки, деталі та підсумки.
- Додано звичайні сумісні індекси; колонки, бізнесові журнали й версія схеми не змінювалися. Немає нових інфраструктурних залежностей. AWS конфігурацію та production дані не змінювали; push і деплой не виконували.

Перевірки: TypeScript, строгий lint, production build; **178** тестів бази й розрахунків, **120** компонентних/HTTP тестів, **240** браузерних сценаріїв на desktop/mobile; після уточнення контрактів повторно пройдено **76** пов’язаних сценаріїв; фінальні **42** сценарії складу й combobox також пройдено після виправлення пошуку під час анімації закриття списку. Локальні API списків та журналу додатково перевірено без входу: `401`. Playwright використовує локальний Vite стенд із тестовими бізнесовими сервісами; складський пошук виконує HTTP запити. Реальні SQL запити перевіряються окремими інтеграційними тестами SQLite, авторизація обробників — тестами з підставленим Clerk контекстом. Це не production E2E перевірка на AWS.

### Ресурсний замір

Відтворення: `npm run benchmark:crm`. Скрипт створює й видаляє окрему тимчасову базу. Набір: **10 000 замовлень, 100 000 складських операцій, 200 матеріалів**. Середовище: локальний ARM64 macOS, Node.js 22.18.0, heap обмежений 512 МБ, GC між етапами. Дані синтетичні; переважна історія розташована до вибраного звітного місяця. Час порожніх місячних джерел зарплат/зведення не використовується як оцінка навантаження реального місяця з нарахуваннями.

| Читання | Час SQL/проєкції | Розмір JSON |
| --- | ---: | ---: |
| 50 замовлень | 5.73 мс | 43 224 байти |
| Пошук замовлень і 50 результатів | 46.84 мс | 43 224 байти |
| 50 матеріалів | 22.82 мс | 11 741 байт |
| 50 складських операцій | 131.10 мс | 24 960 байтів |
| Одна картка замовлення | 0.96 мс | 1 631 байт |
| Огляд: підсумки й історичні тренди | 280.54 мс | 10 879 байтів |
| Старий повний пакет CRM на цій базі | 452.20 мс | 11 149 858 байтів |
| Старий повний склад із журналом | 1104.05 мс | 49 846 931 байтів |

Пік RSS процесу до запуску старих повних читань — приблизно **184 МіБ**; він включає генератор, TypeScript loader і SQLite. Це замір локального процесу читання, який не включає повний Next.js сервер, затримку Clerk, HTTP передачу та паралельних користувачів. Він показує зменшення обсягу й пам'яті, але не є гарантією місткості AWS сервера з 2 ГБ. Поточну схему одного застосунку з SQLite збережено; фактичне навантаження AWS потрібно оцінювати окремо при розгортанні.
